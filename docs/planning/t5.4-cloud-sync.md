## 1. Obiettivo

Aggiungere al LayerCost attuale, senza rompere la modalità locale:

- due utenti con login;
- un database Postgres gestito;
- un archivio **condiviso** di configurazione e preventivi;
- sincronizzazione tra due dispositivi;
- backup, export e continuità operativa su piani gratuiti.

L'app deve continuare a funzionare **senza account e senza rete**. Il cloud è un livello aggiuntivo, non un requisito.

### 1.1 Criteri di successo

- Due dispositivi, dopo il login, vedono gli stessi preventivi e la stessa configurazione.
- Senza rete l'app resta usabile in locale; le modifiche in sospeso vengono sincronizzate al ritorno.
- Un conflitto è visibile e risolvibile; nessun dato viene sovrascritto in silenzio.
- Un utente non può leggere o modificare dati di un workspace a cui non appartiene.
- Il piano resta €0: Supabase Free, Vercel Hobby, GitHub Actions free.
- Export JSON sempre disponibile; backup automatico prima del primo sync e backup periodico lato database.
- `npm run check`, E2E, axe e regressione visiva restano verdi.

## 3. Architettura

### 3.1 Livelli

```text
UI (React)
  │
  ▼
state/app-store.ts
  │  ├── localRepository (guest, localStorage)
  │  └── cloudRepository (Supabase, opzionale)
```

Regole:

- `domain/` non importa Supabase, React o storage.
- `data/cloud/` è l'unico punto che conosce Supabase.
- `state/` orchestra; non implementa formule.
- `features/auth` e `features/sync` usano store e componenti.
- Il client Supabase viene importato dinamicamente: chi non accede non scarica il chunk.

### 3.2 Contratti

```ts
// data/repository.ts — contratto locale, reso asincrono
interface DataRepository {
  load(): Promise<LoadResult>
  save(data: AppData): Promise<void>
  export(data: AppData): Promise<void>
  import(file: File): Promise<AppData>
  reset(): Promise<AppData>

```

```ts
// data/cloud/gateway.ts — sync per entità, separato dal repository locale
interface CloudGateway {
  pull(): Promise<CloudSnapshot>
  push(changes: ChangeSet): Promise<PushResult>
  health(): Promise<void>

```

`DataRepository` non deve diventare un contenitore di logica di merge. La sincronizzazione è un caso d'uso separato, con test propri.

| Modalità | Dati | Rete | Note |
| --- | --- | --- | --- |
| Ospite | `layercost:data` | Non richiesta | Comportamento attuale, invariato |

## 4. Autenticazione

### 4.1 Flusso

1. L'utente apre `#/login`.
2. Inserisce email e password.
3. Supabase restituisce una sessione; il client la persiste.
4. L'app carica il workspace e i dati cloud.
5. Se non esiste una membership, mostra "Nessuno spazio associato" e le istruzioni per l'amministratore.
6. Logout da Impostazioni → Sincronizzazione.

### 4.2 Regole

- Signup pubblico disabilitato nel dashboard Supabase.
- Utenti creati manualmente con auto-confirm.
- Nessun link "Password dimenticata" finché non c'è SMTP: il reset è amministrativo.
- Password minima 12 caratteri, gestita nel dashboard.
- Sessione persistita da `supabase-js`; refresh token rotation attiva.
- Errori di login generici: non rivelare se un'email esiste.
- Rate limit di Supabase attivo; niente CAPTCHA nella prima iterazione.
- Nessuna service role key nel bundle o nelle variabili Vercel.

### 4.3 Rotte

- `#/login` — pubblica; se già autenticato, redirect alla route precedente o al calcolatore.
- `#/settings` — sezione "Sincronizzazione" con stato, account, sync ora, esci, backup.
- Nessuna route protetta globale: il calcolatore resta accessibile in modalità ospite.
- Se l'ambiente non ha `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY`, la UI cloud è nascosta e l'app resta local-only.

### 5.3 `workspace_members`

| Colonna | Tipo | Note |
| --- | --- | --- |

| `user_id` | `uuid` FK | `auth.users(id)` |
| `role` | `text` | `owner` o `editor`; nella prima iterazione entrambi `owner` |
| `created_at` | `timestamptz` | Default `now()` |

PK `(workspace_id, user_id)`, indice su `user_id`.

### 5.4 Entità di configurazione

Tutte hanno:

- `id text` PK;
- `workspace_id text` FK;
- `created_at`, `updated_at timestamptz`;
- `created_by`, `updated_by uuid`;
- `archived_at`, `deleted_at timestamptz` opzionali.

Tabelle:

- `settings` — una riga per workspace, campi scalari di `Settings` (le tariffe stanno in `energy_tariffs`).
- `energy_tariffs` — `label`, `price_per_kwh` in µ€, `effective_from date`, `notes`.
- `printers` — campi di `Printer`; `build_volume_mm integer[]` con check su 3 elementi; `power_profiles jsonb`.
- `materials` — campi di `Material`.
- `extras` — campi di `Extra`.

Unicità: nessun vincolo sul nome, perché l'app permette nomi duplicati. Indici su `(workspace_id, deleted_at)` e `(workspace_id, updated_at)`.

Check:

- `jsonb_typeof(lines) = 'array'`;

- `status in ('saved','sent','completed')`;
- `locale in ('it','en')`.

La validazione economica completa resta in Zod e nel dominio. Il database valida struttura, stato e appartenenza, non le formule.

### 5.6 Trigger

1. **`set_updated_at`** su tutte le tabelle mutabili: `updated_at = now()`.
2. **`set_updated_by`** su configurazione e preventivi: `updated_by = auth.uid()`.
3. **`protect_locked_quote`**:
   - se `OLD.status = 'sent'` o `'completed'`, rifiuta modifiche a campi economici (`lines`, `job`, `pricing`, `snapshot`, `result`, `name`, `customer`, `quote_date`, `locale`, `engine_version`);
   - consente solo `archived_at` e `updated_at`;
   - rifiuta transizioni all'indietro (`completed → sent/saved`, `sent → saved`).
4. **`protect_last_owner`** (opzionale, consigliato): impedisce di rimuovere l'ultimo `owner` di un workspace.

### 5.7 RLS

Helper:

```sql
create or replace function public.is_workspace_member(target_workspace_id text)
returns boolean
language sql
stable
security definer
set search_path = ''
as $$
  select exists (
    select 1
    from public.workspace_members m
    where m.workspace_id = target_workspace_id
      and m.user_id = auth.uid()
  );
$$;

-- Analogo: is_workspace_owner(target_workspace_id) con `m.role = 'owner'`.
-- Entrambe le funzioni sono security definer e non risolvono le RLS della tabella.
```

Regole:

- `workspaces`: `select` se membri; `update` solo owner; `delete` negato.
- `workspace_members`: `select` se membri dello stesso workspace; insert/update/delete solo owner.
- `settings`, `energy_tariffs`, `printers`, `materials`, `extras`, `quotes`: `select`, `insert`, `update` se membri; `delete` negato.
- Nessuna policy `using (true)`.
- Nessuna service role key nel client.
- Test con due utenti: un utente non vede né modifica il workspace dell'altro.

La creazione di workspace e membership è amministrativa nella prima iterazione (SQL nel runbook). Non c'è una policy di insert per utenti autenticati.

### 5.8 Accesso amministrativo

- `service_role` ha grant completi sulle tabelle solo per script amministrativi (bootstrap, E2E, backup): non viene mai usato dal client né messo nel bundle.
- `protect_last_owner` protegge gli utenti autenticati, ma consente alle richieste senza subject JWT (service role o SQL admin) di rimuovere l'ultimo owner, così la cancellazione di un workspace può fare cascade su tutte le tabelle.
- Il cleanup dei workspace di test usa `delete from public.workspaces` con le FK attive; non disabilita `session_replication_role`, che lascerebbe righe orfane.

## 6. Sincronizzazione

### 6.1 Dati e direzione

| Dato | Sincronizzato | Note |
| --- | --- | --- |
| `Settings` scalari | Sì | Last-write-wins con conflitto visibile |
| `EnergyTariff` | Sì | Per entità |
| `Printer` | Sì | Per entità |
| `Material` | Sì | Per entità |
| `Extra` | Sì | Per entità |
| `Quote` | Sì | `saved` modificabile, `sent`/`completed` bloccati |
| Bozza | No | Locale |
| Tema | No | Locale |
| Lingua | No | Locale |
| Onboarding | No | Locale |

### 6.2 Pull

1. Al login, all'avvio con sessione, al focus della finestra e su "Sincronizza ora".
2. Lettura completa di configurazione e preventivi non cancellati (i tombstone servono per la cache).
3. Mappatura righe → tipi di dominio con Zod.
4. Aggiornamento della cache cloud.
5. Se il pull fallisce, l'app resta sulla cache e mostra lo stato `offline`/`error`.

Per due utenti il volume è piccolo; il pull completo è accettabile. Un pull incrementale per `updated_at` è un'ottimizzazione successiva, non necessaria nella prima iterazione.

### 6.3 Push

1. Le modifiche vengono applicate in modo ottimistico allo stato UI.
2. Se online, la scrittura va subito a Supabase.
3. Se offline, l'operazione entra nell'outbox con:
   - entità, ID, tipo (`insert`/`update`/`archive`/`softDelete`);
   - payload;
   - `expectedUpdatedAt` per le update;
   - timestamp locale e numero progressivo.
4. Al ritorno della rete, l'outbox viene riprodotta in ordine.
5. Insert idempotenti: se l'ID esiste già, non si duplica.
6. Update con controllo `updated_at`: se il record è cambiato nel frattempo, si ferma la coda e si apre il conflitto.

### 6.4 Conflitti

| Caso | Comportamento |
| --- | --- |
| Preventivo `saved` modificato da entrambi | Modale: "Ricarica la versione remota" o "Duplica le mie modifiche" |
| Preventivo `sent`/`completed` modificato | Rifiuto: il preventivo è bloccato; offri "Duplica" |
| Stampante/materiale/tariffa/extra modificato da entrambi | Modale: "Mantieni locale" / "Usa remoto" |
| Impostazioni modificate da entrambi | Last-write-wins con avviso e timestamp |
| Entità cancellata/archiviata da remoto | Rimuovi dalla vista, mantieni tombstone in cache |
| Stesso ID inserito da due dispositivi | Idempotente; vince il primo, il secondo ricarica |

Nessun overwrite silenzioso. Il conflitto è persistito finché l'utente non sceglie.

### 6.5 Primo login

| Stato cloud | Stato locale | Comportamento |
| --- | --- | --- |
| Vuoto | Con dati | Offri "Importa i dati locali"; scarica backup JSON prima |
| Vuoto | Vuoto | Nessuna azione; usa il seed |
| Con dati | Vuoto | Carica il cloud |
| Con dati | Con dati | Il cloud vince; scarica backup JSON e mantieni `layercost:data` intatto |

Nessun merge automatico nella prima iterazione. Il merge per entità è un task successivo, solo se richiesto.

### 6.6 Logout

- Verifica outbox vuota; se non lo è, chiedi conferma.
- Rimuovi sessione e cache cloud.
- Torna alla modalità ospite con `layercost:data`.
- Il cloud non viene cancellato.

## 8. Operazioni sul piano gratuito

### 8.1 Limiti verificati

| Backup automatici | Non inclusi |
| Email integrate | 2/ora |
| Ripristino progetto in pausa | Fino a 1 anno (documentazione attuale) |

### 8.2 Keep-alive

- RPC `public.keepalive()` che esegue `select 'ok'`; `security definer`, `search_path = ''`; `grant execute` ad `anon`.
- GitHub Action giornaliera che chiama la RPC con URL e chiave pubblicabile da secret.
- Se la chiamata fallisce, il workflow apre/aggiorna una issue o notifica il committente.
- La documentazione Supabase indica che "qualche richiesta al database al giorno" è sufficiente; una volta al giorno è più prudente di ogni 2–3 giorni.

### 8.3 Backup

- Workflow settimanale `pg_dump` via **session pooler** (IPv4), non connessione diretta IPv6.
- Compressione e cifratura simmetrica con secret GitHub; artifact con retention 30 giorni.
- Verifica di restore su un progetto locale o su un secondo progetto Free almeno una volta.
- L'export JSON dell'app resta disponibile e viene proposto prima del primo sync.
- Consapevolezza: il Free non ha backup automatici; il backup è responsabilità del progetto.

### 8.4 Email

- Nessun SMTP nella prima iterazione.
- Il servizio integrato (2/ora) non è usato per il login.
- Reset password: dashboard Supabase o Admin API con service role, eseguito dall'amministratore, mai dal client.
- Se in futuro serve il reset self-service: Brevo/Resend free + template Supabase, senza cambiare schema o RLS.

### 8.5 Progetti

- Un progetto cloud `layercost-prod` in regione EU.
- Sviluppo e test con **Supabase locale** (CLI + Docker), non con un secondo progetto cloud.
- Se serve uno staging cloud, usare il secondo slot Free e metterlo in pausa quando non serve.

### 8.6 Bundle e performance

- `@supabase/supabase-js` importato dinamicamente in `data/cloud/client.ts`.
- Il chunk cloud non deve essere caricato in modalità ospite.
- Aggiornare `scripts/check-budget.mjs` con un budget separato per il chunk cloud (misurare prima di fissarlo).
- Il budget separa **JS iniziale** (205 KB), **chunk lazy** (80 KB), **worker .3mf** (40 KB) e **totale iniziale** (350 KB). T5.4.4 ha misurato 201,9 KB iniziali e 53,5 KB cloud con env; il worker è 37,6 KB e il totale iniziale 266,7 KB.

### 8.7 Deploy

- Vercel: `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` per Production e Preview.
- Nessuna variabile obbligatoria: se mancano, l'app resta local-only.
- Supabase Auth: Site URL `https://layercost.vercel.app`; redirect URL `http://localhost:5173/**` e produzione. Con password auth i redirect non sono critici.
- Se in futuro si aggiunge CSP, includere `connect-src https://*.supabase.co`.
- Vercel Hobby resta per uso personale; se l'app diventa commerciale, valutare Cloudflare Pages/Netlify.

Le scritture offline restano in coda; al ritorno della rete vengono riprodotte. Una modifica arrivata durante un push non viene persa: l'operazione resta in coda con il nuovo `updated_at`.

- **Stato e indicatore:** `SyncIndicator` in sidebar/menu con testo oltre al colore; `SyncSettings` mostra stato, account, ultimo sync, pending, errore, conflitto, sync manuale, backup e logout. Al logout con modifiche in sospeso viene chiesto conferma; cache e outbox restano nel browser per il prossimo accesso.

```sql
insert into public.workspaces (id, name)

insert into public.workspace_members (workspace_id, user_id, role)
```

## 12. Rischi

| Rischio | Impatto | Mitigazione |
| --- | --- | --- |
| Pausa del progetto Free | Sync fermo | Keep-alive giornaliero; app local-only; restore fino a 1 anno |
| Nessun backup automatico | Perdita dati | `pg_dump` settimanale + export JSON |
| RLS errata | Dati esposti | Test con due utenti; nessuna policy `true`; review SQL |
| Conflitti di sync | Dati sovrascritti | `updated_at` ottimistico; modale; outbox |
| Budget bundle | Build oltre soglia | Import lazy; budget separato per il chunk cloud |
| Vercel Hobby commerciale | ToS | Uso personale; migrazione a Cloudflare/Netlify se serve |
| Limiti Free che cambiano | Costi o stop | Architettura local-first; export; provider sostituibile |
| Password reset manuale | Utente bloccato | Runbook admin; SMTP free in futuro |
| localStorage pieno | Cache incompleta | Monitorare; valutare IndexedDB in un task successivo |
| Doppio inserimento | Preventivi duplicati | ID client + insert idempotente |
